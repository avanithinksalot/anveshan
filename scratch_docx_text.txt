AI-Powered MPLADS Anomaly, Fraud & Inefficiency Detection Platform
Technical Solution Document — SIH 2026, Problem Statement 26102
Organization: MoSPI | Department: Data Informatics & Innovation Division (DIID) | Category: Software | Theme: Smart Automation
1. Executive Summary
The proposed system is a layered detection platform that turns raw MPLADS operational data — allocation, recommendation, sanction, completion, expenditure and calamity-consent records — into prioritized, explainable risk signals for auditors, District Authorities, State Nodal Departments, MPs, and the Ministry. It combines four detection mechanisms rather than relying on a single model:
Hard rule checks — deterministic violations of explicit MPLADS rules (1-year completion window, disallowed categories, allocation ceilings, SC/ST quotas).
Statistical anomaly detection — unsupervised outlier scoring (Isolation Forest) on cost, timeline and vendor-concentration features.
Supervised risk scoring — an XGBoost model trained on rule-flag and anomaly-score patterns, calibrated with SHAP explanations so every flag has a human-readable reason.
Similarity detection — text similarity for duplicate/near-duplicate works and perceptual image hashing for reused completion photos.
All four feed a single composite Risk Score (0–100) per work, surfaced through role-based dashboards, with an auditor feedback loop that improves the model over time.

3.1 Join key & master lifecycle table
Every work carries an identifier of the form WS/MP<id>/<year>-<year>/<serial> embedded as a prefix inside the “Work” field. Extracting this via regex into a clean work_id column makes all six tables joinable. The pipeline builds one master table, one row per work:
Recommended Amount → Sanction Amount → Σ(Expenditure Fund Disbursed) → Completion Date → Work Status
This master table is what every downstream feature and model operates on.

Strip footer/summary rows (e.g. a “Grand Total” row was found sitting inside Works_Sanctioned).

Treat “Image” values of literal N/A or the non-descriptive placeholder “Images” as missing until actual image files/URLs are confirmed available from the portal.
Handle garbled/mis-encoded regional-language text in Work Description with a language-aware cleaning step rather than dropping those rows.

5. End-to-End Workflow
Extract the six source tables (batch export today; direct DB/API connection in production).
Clean: drop footer rows, normalize currency/date fields, extract work_id, normalize entity names (MP, IDA, Vendor).
Join into the master lifecycle table (Recommended → Sanctioned → Completed → Expenditure, keyed on work_id).
Compute engineered features (Section 6) at work-level, vendor-level and MP-level granularity.
Apply the deterministic rule engine — any hard violation is auto-flagged regardless of ML score.
Run Isolation Forest on continuous features to produce an unsupervised anomaly score per work.
Run the XGBoost classifier (trained on rule-flag patterns + anomaly scores + validated CAG-report cases) to produce a calibrated risk probability.
Run SHAP on the XGBoost output to generate a human-readable reason string per flagged work.
Combine rule flags + Isolation Forest score + XGBoost probability into one composite Risk Score (Section 8) and store it.
Serve the results via FastAPI to role-based React dashboards; auditors mark cases cleared / escalated / under investigation.
Feed auditor decisions back as labels for the next training cycle (active learning loop).

7. Machine Learning & AI Components — Detail
7.1 Rule Engine (deterministic layer)
Runs first, before any ML scoring. Encodes explicit, citable MPLADS rules rather than statistical guesses:
Sanction-to-completion must not exceed 1 year — violation → automatic high-risk flag.
Total (Disbursed + Calamity Consent) must not exceed a MP's Allocated Amount.
Funds must not go to religious structures, private trusts/individuals, or non-durable assets — keyword/classifier check against description text.
SC/ST allocation quotas (15% / 7.5%) must be met across an MP's yearly portfolio.
Because these are direct rule violations, they bypass the probabilistic score and are surfaced at maximum priority — this keeps the system defensible and auditable, since a human reviewer can trace every hard flag straight back to a named scheme rule.
7.2 Isolation Forest (unsupervised anomaly detection)
Applied to continuous work-level and vendor-level features (cost ratios, durations, concentration scores). Chosen because MPLADS has no reliable labeled fraud dataset — Isolation Forest needs no labels; it isolates points that are statistically far from the bulk of the data via random recursive partitioning, and outputs an anomaly score per record. This catches novel patterns that were never anticipated at rule-design time.
7.3 XGBoost + SMOTE (supervised risk scoring)
Stage-two model. Training labels come from three sources: (a) hard rule violations from Section 7.1, (b) top-ranked Isolation Forest anomalies, and (c) known irregularity cases sourced from published CAG audit reports on MPLADS — used as genuine, citable ground truth rather than only synthetic fraud injection. Because true positives are rare, SMOTE (Synthetic Minority Oversampling) balances the training set before fitting XGBoost, which then outputs a calibrated 0–1 risk probability per work using gradient-boosted decision trees over all engineered features.
7.4 SHAP (explainability layer)
Wraps the XGBoost output to attribute the score to specific features — e.g. “flagged due to 340% cost deviation from category median + vendor active across 6 districts.” This is what makes the score usable by a non-technical district auditor and defensible in an official report, rather than an opaque number.
7.5 Text similarity (duplicate/fake work detection)
TF-IDF vectorization of Work Description + cosine similarity (scikit-learn), backed by rapidfuzz for fast fuzzy string matching on shorter fields (Work name, IDA name). Any pair of works above a similarity threshold, especially across different constituencies, is flagged for manual comparison. A multilingual sentence-embedding model (e.g. a Sentence-Transformers multilingual variant) is a natural upgrade path once Hindi/regional-language description quality is confirmed clean.
7.6 Perceptual image hashing (duplicate completion photo detection)
Uses the imagehash library (difference hashing / pHash) to fingerprint each completion image and detect near-identical images reused across different “completed” works — a strong, visually demonstrable fraud signal. A basic pretrained image classifier (e.g. a lightweight CNN or vision-transformer checkpoint) can additionally sanity-check that an image plausibly matches its declared Work Category (e.g. a road vs. a hall) as a stretch goal; full satellite before/after change detection (e.g. on open Sentinel-2 imagery) is scoped as future work rather than hackathon-timeline scope.
8. Composite Risk Scoring & Case Management
Every work receives one Risk Score from 0–100:
Any hard rule violation (Section 7.1) → score fixed at 80–100, regardless of ML output.
Otherwise: Risk Score = 40% × normalized Isolation Forest anomaly score  +  40% × XGBoost risk probability  +  20% × (vendor concentration score + similarity score, averaged).
Risk tiers for the dashboard: Low (0–39, informational only), Medium (40–69, periodic review queue), High (70–100, immediate auditor attention).
Every flagged work carries its SHAP-derived reason string and links back to the exact source rows (recommendation, sanction, completion, expenditure) so an auditor can verify the underlying facts, not just trust the score.
Figure 7: How the composite Risk Score is calculated, and the resulting risk tiers.
8.1 Case lifecycle
Flagged → Under Review → Cleared / Escalated / Confirmed Irregularity. Every transition is logged with the reviewing authority's role and timestamp, and confirmed/cleared outcomes become new training labels for the next XGBoost retraining cycle.

12. Evaluation Strategy
Ground-truth validation: run the trained model against known irregularity cases published in CAG audit reports and report how many the model would have flagged.
Rule-violation recall: 100% by construction for hard-rule checks (1-year rule, allocation ceiling, disallowed categories) since these are deterministic.
Precision on ML-only flags: manual audit-style review of a sample of Medium/High tier flags that are not hard-rule violations.
Continuous evaluation: auditor clear/escalate/confirm decisions logged and used to track precision drift over time.
13. Deployment & Scalability
The current tables (85K+ expenditure rows, 35K+ completed works) run comfortably on a single-node batch pipeline. The architecture scales horizontally: the ETL/feature/scoring stages are stateless batch jobs that can be sharded by state, and PostgreSQL/FastAPI scale independently of the ML layer. A scheduled batch run (daily or weekly, matching the portal's own update cadence) re-scores new and updated works; no real-time streaming is required for the current data-availability model.
14. Limitations & Future Scope
No official MPLADS fraud ground truth exists publicly — mitigated via CAG report cross-validation, but should be stated plainly to reviewers.
Completion images are largely unavailable in the current export (placeholder “Images” text rather than files/links) — duplicate-image detection needs a confirmed image data source from the Ministry.
Fund-misuse (category drift) detection depends on the work_id remaining consistent across the sanction and completion stages; this should be validated on the full dataset before being presented as a fully solved capability.
Cost-overrun detection currently compares Disbursed vs. Sanctioned amount; adding state PWD Schedule-of-Rates benchmarks would turn this into an even stronger “% above official government rate” metric.
Full satellite-based before/after construction verification is scoped as a future phase requiring integration with open satellite imagery (e.g. Sentinel-2) and is not part of the current build.
Regional-language (Hindi and other) text in Work Description shows encoding issues in the current export; a language-aware cleaning/OCR step would improve text-similarity accuracy.
